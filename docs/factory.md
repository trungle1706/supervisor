# Agent factory (phase 12B): schemas, harness, catalogue, editor

WP-F1. Pure modules in `src/supervisor/factory/`; no flag. The one route sits behind
`ONBOARD_FACTS`. The platform locks the schemas, the tool registry and the mandatory guardians.
A team edits the listed fields only. All limits are in one file, `src/supervisor/factory/caps.py`;
the tables below are generated by hand from it, and a change to a cap is a platform change.

## Schemas

Three frozen schemas, version 1. Each is a pydantic model with `extra=forbid` (an unknown key is
refused and named). No float anywhere: counts and scores are integers, confidence is an enum.

```text
 facts card ---- GET /v1/facts/{node_id}/export ----> facts_v1
 agent definition (YAML or JSON) ---- validate ----> agent_definition_v1
 agent run ------------------------------------------> assessment_report_v1
```

Windows cmd:

```text
python -m supervisor.factory validate tests\factory\data\agent_single_pass.yaml
python -m supervisor.factory validate report.yaml --schema assessment_report_v1
python -m supervisor.factory schema agent_definition_v1 > agent_definition_v1.schema.json
```

`validate` prints `[OK]` and exits 0, or one `[FAIL] <field>: <message>` line per error and exits 1.
It never prints a traceback. For an agent definition it also checks the registry files (tool ids,
modes, scope kinds, group, owned dimension).

### facts_v1 (export of the facts card)

| Field | Type | Note |
|---|---|---|
| `version` | `1` | frozen |
| `node_id`, `attempt_n`, `latest_attempt`, `newer_attempt` | text, int or null, int or null, bool | from the card |
| `total`, `dropped_claims` | int | counts |
| `facts[]` | `FactRecord` | one per fact, in card order |
| `summary` | `SummaryRecord` or null | the build summary row (`kind=summary`) |

`FactRecord`: `fact_id`, `node_id`, `attempt_n`, `kind`, `name`, `detail`, `file`, `line`, `quote`,
`source` (`rule` / `model`), `confidence` (`low` / `medium` / `high`), `model_id`,
`dropped_claims`, `created_at`. Kinds: `tool`, `model`, `endpoint`, `dataset`, `file`,
`secret_use`, `external_url`, `mcp_server`, `approval_point`, `autonomy`, `decision33`,
`weak_spot`, `claim`.

`confidence` is not stored on a row. It is derived: a rule fact is `high`, a model fact is
`medium` (a model claim that passed `validate_llm_claims`). Drift rule: a test fails when
`onboard.facts.row_view` or `FactsService.card` gains a field that the export does not carry, or
when the fact kinds differ. Add the field to `facts_v1.py` on purpose.

Route: `GET /v1/facts/{node_id}/export`, permission `systems.view`. Off (`ONBOARD_FACTS=0`):
HTTP 400 `facts_off`. A node with no built card answers an export with `attempt_n: null` and no
facts.

### assessment_report_v1

`report_id`, `agent_id`, `agent_version`, `system_id`, `dimension_id` (one of the eight:
`model`, `data_governance`, `cybersecurity`, `legal_compliance`, `ethics`, `third_party`,
`supply_chain`, `reputation`), `findings[]`, `summary`, `model_id`, `harness_trace`, `created_at`
(RFC 3339 UTC, `...Z`).

* `findings[]`: `finding_id` (unique), `checklist_id`, `verdict` (`pass` / `fail` /
  `not_applicable` / `question`), `evidence[]`, `rationale` (at most 600 characters),
  `confidence` (`low` / `medium` / `high`).
* `evidence[]`: `kind` (`fact` / `document` / `regkb` / `pack` / `system_record`), `ref`, `file`,
  `line` (a line needs a file). **A finding with verdict `pass` or `fail` and no evidence is
  invalid.**
* `summary`: `total`, `passed`, `failed`, `not_applicable`, `questions` (integers; must equal the
  counts of `findings`).
* `harness_trace`: integers and pointers per component: `system_prompt`, `context`, `memory`,
  `hitl`, `verification`, `loop` (with `stopped_by` and `per_iteration[]` holding the score and a
  pointer `reason_ref` to the logged evaluator reason). It never holds document text.

### agent_definition_v1

| Field | Locked or editable | Rule |
|---|---|---|
| `schema_version` | locked | `"1.0"` |
| `id` | immutable | lowercase letters, digits, hyphen; at most 64 |
| `name` | editable | 1 to 64 characters |
| `description` | editable | 1 to 1,024 characters |
| `owner_group` | set at creation | `model_risk`, `data`, `cyber`, `legal`, `third_party`, `ethics`, `platform` |
| `dimension_id` | set at creation | one of the eight; the group must own it |
| `policy_refs[]` | editable | `doc_id`, `source` (`regkb` / `internal`), `version`, `sections[]`; at most 20 |
| `checklist[]` | editable | `id`, `question` (at most 500), `evidence` kinds, `severity` (`low` / `medium` / `high`), `pass_rule` (at most 500); 1 to 60 items; evidence kinds must be in `evidence_rules.allowed_sources` |
| `evidence_rules` | editable | `allowed_sources`, `must_cite` (locked `true`), `max_age_days` (1 to 3,650) |
| `tools[]` | editable inside the group allow-list | `tool_id`, `scope`, `mode` (`read` / `propose`) **by reference only**; an inline tool definition is refused; at most 12 |
| `instructions` | editable | text, at most 5,000 tokens (estimate: UTF-8 bytes / 4), linted |
| `harness` | see below | every field checked against `caps.py` |
| `output_schema` | locked | `{type: assessment_report_v1}` |
| `guardians[]` | mandatory part locked | must contain `pii_mask_v2`, `tool_scope_guard`, `citation_required`; extra guardian ids allowed |
| `eval_pack` | editable | pack id |
| `lifecycle` | platform | `state` (`draft` / `tested` / `approved` / `live` / `retired`), `version` (`1.2` or `1.2.3`), `approvals[]` |

The instruction linter refuses control characters and text that tries to override the platform
preamble (for example "ignore all previous instructions").

### Registry files

`config/factory_tools.yaml`: per tool `tool_id`, `label`, `kind` (`read_facts`, `read_regkb`,
`read_pack_results`, `read_system_record`, `search_documents`), `scope` (kinds `system`, `regkb`,
`pack`, `documents`), `data_class`, `allowed_groups`, `modes` (`read`, `propose`). A tool ref
`scope: "regkb:SBV-TT53-2025"` must use a scope kind of the tool.

`config/factory_groups.yaml`: per group `label`, `roles` (roles of `config/users.yaml` that may
author for the group) and `dimensions` (the dimensions the group owns; each dimension has one
owner). Both loaders (`supervisor.factory.registry`) use strict keys: an unknown or missing key
is an error that names the file and the field.

## Harness

Every agent definition has a `harness` block with six components. Each has a platform default (the
locked part), a bounded editable part and a gate test (WP-F3). Nothing in the harness can call a
tool outside the registry, write outside the run, or act on a bank system. Omit a component to
get its default.

### system_prompt

| | |
|---|---|
| Default (locked) | the platform preamble `platform_v1`: role, output schema, evidence rule, refusal rules, masking rule; always first |
| Editable | the top-level `instructions`, appended after the preamble |
| Cap | 5,000 tokens; linter; `harness.system_prompt.preamble` must be `platform_v1` |

### context

| Field | Default | Editable | Cap |
|---|---|---|---|
| `sources` | `facts_v1`, `pack_results`, `system_record`, `regkb_rows`, `document_sections` (this order) | which sources and their order | only these five, no repeat, at least one; `document` evidence needs `document_sections` |
| `budget_tokens` | 12,000 | yes | 1,000 to 24,000 per call |
| `max_document_chars` | 8,000 | yes | 0 to 20,000 |
| `progressive` | `true` (names first, bodies on demand) | no | locked `true` |

### memory

| Field | Default | Editable | Cap |
|---|---|---|---|
| `run` | `scratchpad` (one run, deleted after) | no | locked |
| `system_memory` | `false` | on or off | when on: `retention_days` and `fields` are required; when off they must be absent |
| `retention_days` | none | with `system_memory: true` | 1 to 365 |
| `fields` | none | `prior_verdicts`, `open_questions`, `waivers` | no repeat |
| `cross_run` | `off` | no | must be `off` in 12B |

No personal data is ever stored; a stored row passes the masker.

### hitl (human in the loop and permissions)

| Field | Default | Editable | Cap |
|---|---|---|---|
| tool modes | `read` only | `permissions[]`: `tool_id` and `mode` (`read` / `propose`) | `act` does not exist; a tool must be in `tools`; a permission cannot widen a `read` tool to `propose` |
| `approval_points[]` | none | `kind: checklist` (a checklist id) or `kind: verdict` (`pass`, `fail`, `not_applicable`, `question`) | at most 20 |
| verdict `fail` on a `high` item; final report | needs a person | no | locked in the runtime |

### verification

| Field | Default | Editable | Cap |
|---|---|---|---|
| `verifier` | `rules` | `rules` or `rules+judge` | the judge re-reads the rationale; it advises |
| locked validators | `evidence_exists`, `quote_matches`, `pass_rule_follows` (always run, before any judge) | no | |
| `validators[]` | none | `evidence_kind_allowed`, `evidence_age`, `rationale_length`, `no_personal_data` | platform list only |

### loop

| Field | Default | Editable | Cap |
|---|---|---|---|
| `mode` | `single_pass` (gather, one structured call per checklist group, verify) | `single_pass` or `loop` | |
| `max_iterations` | 1 | with `mode: loop` | 1 to 8; must be 1 for `single_pass` |
| `stop_when` | `[all_answered]` | `all_answered`, `evaluator_done` | `evaluator_done` needs `mode: loop` |
| `loop_evaluator` | `rules` (coverage, evidence present) | `rules` or `judge` (advisory) | only `rules` for `single_pass` |
| `min_score` | none | required with `judge` | integer 0 to 100; refused with `rules` |
| `budget_tokens` | 60,000 | yes | 1,000 to 200,000 per run |

### Cross-field checks

* every `harness.hitl.permissions[].tool_id` is in `tools`;
* every `approval_points` checklist ref exists;
* the registry check (`python -m supervisor.factory validate`) tests tool ids, modes, scope kinds,
  group access and dimension ownership.

### Choices the platform made (change in `caps.py` on purpose)

The plan fixed `instructions` (5,000 tokens), `retention_days` (365), `max_iterations` (8) and the
modes. The values for the context budget (24,000), the loop budget (200,000), `max_document_chars`
(20,000), the integer score scale (0 to 100) and the three mandatory guardian ids were chosen in
WP-F1 and need the hub to confirm.

## Catalogue

WP-F2. Flag `AGENT_FACTORY=1` (default `0`; needs `GOVERNANCE_ENABLED=1`; Windows cmd:
`set AGENT_FACTORY=1`). Off: every route answers HTTP 400 `agent_factory_off` and no factory table is
read. The routers are always mounted.

```text
 template (config/factory_templates/<dimension>.yaml)
        |  create_from_template
        v
 factory_agent  (id, version) --- draft --- retire ---> retired       WP-F3: tested, approved, live ("Promotion")
        |  save_draft: agent_definition_v1 + registry on every save
        |  new_version: copy to the next minor version (one open draft per agent)
        v
 factory_agent_event (append only): created, saved, new_version, retired,
                                    helper_accepted, helper_dropped, golden_uploaded
```

### Tables (appended at the end of `schema/model.yaml`)

| Table | Kind | Key | Columns |
|---|---|---|---|
| `factory_agent` | state | `id`, `version` | `owner_group`, `dimension_id`, `definition_json` (an `agent_definition_v1`), `state`, `created_by`, `updated_at`, `row_version` |
| `factory_agent_event` | append only | `event_id` | `agent_id`, `version`, `kind`, `actor_ref`, `detail` (masked, at most 300 characters), `created_at` |
| `factory_helper_draft` | state | `draft_id` | `agent_id`, `version`, `helper`, `row_json`, `status` (`draft` / `accepted` / `dropped`), `model_id`, `prompt_version`, `run_id`, `decided_by`, `decided_at`, `created_at` |

`factory_helper_draft` is a third table that the plan did not list: the helper agents need a
draft-then-accept table like `regkb_draft`.

### Store API (`supervisor.factory.store`, for WP-F4 and WP-F3)

`FactoryStore(state, tables, clock, tools=None, groups=None)`; a row is a dict with the columns and
`definition` (the parsed `definition_json`). A refusal is `FactoryError` (a `SupervisorError`, HTTP 400)
whose text starts with a code (`invalid_definition`, `exists`, `not_found`, `not_draft`, `stale`,
`draft_open`, `bad_transition`, `reason_needed`) and, for a definition, lists `field: message` pairs.

| Call | Does |
|---|---|
| `create_from_template(dimension_id, agent_id, name, actor) -> row` | draft `0.1` from the template; the owner group is the owner of the dimension; event `created` |
| `save_draft(agent_id, version, definition, actor, expected_version) -> row` | draft only; `id`, `owner_group`, `dimension_id` cannot change; state and approvals are forced; validates with `agent_definition_v1` and the registry; optimistic `row_version`; event `saved` |
| `new_version(agent_id, from_version, actor) -> row` | next minor version as a draft; refused while a draft is open |
| `retire(agent_id, version, actor, reason) -> row` | draft to retired, with a reason |
| `get(agent_id, version=None)`, `versions(agent_id)` | one row (the newest when no version), all versions in order |
| `list_agents(owner_group=None, dimension_id=None, state=None)` | the newest version of every agent, by dimension then id |
| `events(agent_id, version=None, limit=None)`, `record_event(agent_id, version, kind, actor_ref, detail)` | the event log |
| `live_agent_for(dimension_id) -> row or None` | the newest `live` version for the dimension (WP-F2 never sets `live`) |
| `portfolio() -> list[dict]` | eight entries `{dimension_id, owner_group, kind: live_agent or rule_proposal, agent_id, version}` |

Module functions: `validate_definition(raw, tools, groups)`, `permits(roles, owner_group, groups)`,
`enabled(settings)`, `require_on(settings)`, and the table `TRANSITIONS` (draft to retired; WP-F3
extends it). The orchestrator (WP-F4) reads `live_agent_for` and `portfolio`; a dimension with no live
agent uses the rule proposal of the risk assessment.

## Editor

`GET /console/factory/{id}?v=<version>&step=<step>` is a full page. Each step is also an HTMX
fragment: `GET /console/factory/{id}/step/{step}` (target `#factory-step`) and `POST` to the same URL to
save it. A POST needs the `HX-Request: true` header (HTTP 400 without it) and carries `version` and
`row_version`. The editor builds a plain definition and calls `save_draft`; it never bypasses the
schema, so a bad value is a 400 that names the field (for example `harness.context.budget_tokens`).

| # | Step | What a person edits | Notes |
|---|---|---|---|
| 1 | template | name, description, eval pack id | dimension, owner group and output schema are shown and locked |
| 2 | policy references | add or drop a row: RegKB instrument id (checked against RegKB) or an internal document id, version, sections | the internal source is a placeholder until WP-W3 |
| 3 | checklist | add, edit, drop rows: id, question, evidence kinds, severity, pass rule | dropping an item also drops an approval point that names it; the checklist drafter sits below the table |
| 4 | tools | tick tools from the allow-list of the owner group, mode and scope | the list shows kind and data class; an inline tool is refused by the schema |
| 5 | instructions | the text, "Check only" (lint without saving) and Save | linter below |
| 6 | harness | one block per component of "Harness" above: the locked default, the editable fields and their caps | context order, budget, memory, approval points and permissions, verifier and validators, loop mode, iterations, stop rules, evaluator, min score, budget |
| 7 | guardians | extra guardian ids | the three mandatory ones are pre-checked, disabled and always saved |
| 8 | preview | pick up to three nodes with a stored facts card | **dry preview**: no model call, no tool call |
| 9 | golden set | upload JSON or CSV; count and stratification; the generator below | WP-F3 adds gate cases and calibration labels (JSON, see "Test gate") |
| 10 | test and promote | gate runs, results, promotion buttons | only with `AGENT_FACTORY_GATE=1` (see "Test gate" and "Promotion") |

### Instruction linter (`supervisor.factory.linter`, phrase list in `config/factory_lint.yaml`)

| Rule | Severity | Meaning |
|---|---|---|
| `tokens` | error / warn | more than the cap (5,000 tokens, estimate bytes / 4) is an error; 80 percent of the cap is a warning |
| `control_chars` | error | control characters other than newline, tab, return |
| `override` | error | text that tries to override the locked preamble |
| `forbidden_phrase` | error | a phrase of the config list ("always pass", "skip the evidence", ...) |
| `checklist_unreferenced` | warn | a checklist id the text never names |

An error blocks the save (the field is `instructions`). The warning does not block a draft; `linter.is_ready`
is false while one is open, and the gate (WP-F3) asks for it before a test run.

### Dry preview and the plan tracer (`supervisor.factory.preview`)

For each chosen node (the stored `facts_v1` export, at most three) and each checklist item the page shows
the evidence kinds, the context sources the harness would load, the registry tool each source goes
through (with the number of facts in the export for `facts_v1`), what is missing (a source not in
`harness.context.sources`, or no tool of the needed kind), whether the item would answer `question`, and
the stop points (approval points and the locked "fail on a high item needs a person"). It also lists the
six harness components. The page labels it "dry preview". It is the plan only; a real run is WP-F4, and
the gate runs the real harness (WP-F3).

### Golden-set store (`supervisor.factory.golden`)

`DATA_DIR/factory/<id>/golden/cases.json`. A case: `case_id`, `checklist_id` (an item of the agent),
`input` (at most 2,000 characters), `expected_verdict`, `note`. A file is at most 1 MB and 500 cases; a
case with the same `case_id` replaces the old one. Every case goes through the Vietnamese masker and a
case that holds a name, phone, account, id number, email or address is refused and listed, never stored.
The page shows the count, the cases per checklist item and per verdict, and the items without a case.

## Helper agents

Owner decision 3. Three helpers, behind `AGENT_FACTORY`, in `supervisor.factory.helpers`. They **draft
only**. Each proposed row is written to `factory_helper_draft` with status `draft`; a person with the
edit right accepts or drops each row, and each accept or drop writes a `factory_agent_event` row
(`helper_accepted`, `helper_dropped`). Like the RegKB drafts (`regkb/drafts.py`).

| Helper | Input | Output | Accept does | Rows dropped before they reach the table |
|---|---|---|---|---|
| `checklist_drafter` | policy section text (pasted; an internal document id arrives with WP-W3) and its pointer | checklist rows with the section pointer | adds the row to the checklist (next free id, the pointer is added to the pass rule) through `save_draft`, so the schema checks it | text too long, severity or evidence kind not allowed, no pointer, text that trips the masker |
| `golden_generator` | the checklist and a count per item (1 to 5) | synthetic Vietnamese cases with expected verdicts | stores the case in the golden set | an unknown checklist id, a bad verdict, **any text that trips the masker** (listed as refused) |
| `result_explainer` | an `assessment_report_v1` JSON (at most 100 KB, validated) | plain sentences with pointers | marks the sentence accepted (shown in the explainer table) | a pointer that is not a `finding_id` of the report, no pointer, text that trips the masker |

The model is the gateway model (`make_chat_model`, see `docs/llm-features.md`). **There is no mock path.**
With `LLM_BASE_URL` empty, or a mock model, the buttons answer HTTP 400 `model_not_configured: model not
configured ...` and nothing is drafted; the editor shows the same notice. Policy text goes through the
secret scrubber before the model sees it. A model error is a 400 message, never a 500. The tests use a
scripted fake `ChatModel`; the product does not.

Windows cmd:

```text
set GOVERNANCE_ENABLED=1
set AGENT_FACTORY=1
set LLM_BASE_URL=http://127.0.0.1:8000/v1
python -m uvicorn supervisor.app:app --port 8130
```

## Runtime (the harness)

WP-F3. `supervisor.factory.runtime.run_agent(definition, inputs, model=None, clock=None)` returns an
`assessment_report_v1` dict. `RoutingRunner` of the orchestrator calls it for a live agent
(`supervisor.factory.catalog.FactoryCatalog` gives the orchestrator the live version of a dimension).
It implements section "Harness" above for `mode: single_pass` and `mode: loop`.

| Component | What the runtime does |
|---|---|
| system_prompt | the platform preamble `platform_v1` first, then the team `instructions` (system message) |
| context | per checklist group (consecutive items that read the same sources): the source index (names) first, then the bodies of the sources the definition names, in its order, while `budget_tokens` has room. A source is read only through a tool the definition holds and inside the tool's scope (`regkb:<instrument>`, `pack:<prefix>`, `documents:<prefix>`). A prompt is never larger than the budget; when the fixed part alone does not fit, no call is made and the items answer `question` |
| model call | one structured `complete_json` call per group; the answer carries `verdict`, `pass_rule_met`, `confidence`, `rationale` and evidence `{kind, ref, file, line, quote}` |
| verification | always: the evidence pointer is a loaded source of an allowed kind, the quote occurs in the loaded text (a quote is required for document and RegKB evidence), the verdict follows the pass rule (`pass` needs `pass_rule_met: true`, `fail` needs `false`), `pass` and `fail` carry evidence. A failed check turns the finding into `question` and counts as rejected. Extra validators: `evidence_kind_allowed`, `evidence_age`, `rationale_length`, `no_personal_data`. `rules+judge` adds one judge re-read that can only lower the confidence |
| hitl | a checklist approval point stops that item before the call; a verdict approval point stops a finding with that verdict. A stopped item gets verdict `question` and the rationale starts with `STOP`. A `fail` on a `high` item counts in `approvals_requested` (the orchestrator then asks for a person) |
| memory | `run` scratchpad lives in the call. With `system_memory: true` and a `memory_dir` in the inputs, rows of ids, enums and dates (`prior_verdicts`, `open_questions`, `waivers`) are masked, stored and pruned by `retention_days` on every read and write |
| loop | iteration 1 is the single pass; the next iterations ask again only for the items still `question`, with the verifier reasons. The evaluator is `rules` (every item has a verdict with evidence) or `judge` (an integer score 0 to 100, `min_score`). Stops: `all_answered`, `evaluator_done`, `max_iterations`, `budget` (the loop `budget_tokens`, capped by the orchestrator budget). The reason of each evaluation is logged (the `log` argument) and the trace holds a pointer |

The trace holds integers and pointers only. The rationale is masked (`pii_mask`) and cut to 600
characters; a document text never reaches the report. With `LLM_BASE_URL` empty the run raises
`model_not_configured`. There is no mock model in the product path; tests pass a fake `ChatModel`.

Inputs: `system` (record), `facts` (facts v1 export), `packs` (`[{ref, label, text}]`, else the pointers of
the rule `proposal` of the orchestrator), `regkb` (`[{ref, text}]`), `documents`
(`[{doc_id, sections: [{ref, text}]}]`), `system_id`, `report_id`, `now`, `budget {seconds, tokens}`,
`memory_dir`. A finding id is `f-<checklist id>`.

## Test gate

WP-F3. Flag `AGENT_FACTORY_GATE=1` (default `0`; needs `AGENT_FACTORY`, and `LLM_BASE_URL` for a run;
Windows cmd: `set AGENT_FACTORY_GATE=1`). Off: every gate route answers HTTP 400 `factory_gate_off`,
no `gate_run` row is read, and the catalogue and editor are unchanged. Editor step 10 "Test and
promote" holds the gate panel and the promotion panel.

```text
  golden gate cases (>= 50, every item)  +  calibration labels (>= 20)
        |
        v
  layer 1  deterministic, all 100 %  ----+
  layer 2  judges + calibration + regression + tier floor ----+--> verdict pass / fail
  layer 3  shadow (information only) -----+                   |
                                                              v
                       signed report (evidence signer)   gate_run row   chain record factory_gate_run
```

| Kind | Layers | Cases | Promotes |
|---|---|---|---|
| `full` | 1, 2 (with calibration and regression), 3 | all | a pass moves a draft to `tested` |
| `sample` | 1 and 2 (judge questions and tier floor only) | default 10, at most 25, stratified by item | never |
| `simulation` | 1 on the reports | the chosen systems (1 to 10) | never (see "Simulation review") |
| `shadow` | 3 | the last N stored onboardings (default 10, at most 25) | never |

A run is a background job: the row is `queued`, then `running` (with progress), then `done` or `failed`
(the run itself broke). The panel polls the step every 2 seconds while a run goes and reloads the page
when the state of the version changed. One run at a time per agent id (`run_in_progress`).
CLI (same code, in this process, ASCII output, exit 0 on a pass):

```text
python -m supervisor.factory gate <agent_id> --kind full|sample [--version 0.1] [--n 10]
```

### Golden gate cases and calibration labels

`DATA_DIR/factory/<id>/golden/gate_cases.json` and `calibration.json`. A gate case is JSON:
`{case_id, inputs: {system, facts, packs, regkb, documents}, expected: {checklist_id: verdict},
expected_evidence_refs: [ref], rubric_notes}`; at most 60 KB of inputs, integers only, every string through
the masker. An F2 case (one text, one verdict) is converted to a gate case with one document section. A
full gate needs at least **50 cases** and **every checklist item** in at least one `expected`
(`golden.gate_stratification`). A label is `{case_id, finding_id, human_verdict, label_by,
labelled_at}`; the upload form on step 9 takes both (JSON). Simulation marks add labels (source
`simulation`).

### Layer 1: deterministic checks (all must be 100 percent)

| Check | Kind | Fails when |
|---|---|---|
| `schema_valid` | per case | the report is not a valid `assessment_report_v1`, names another agent, version or dimension, or does not cover the checklist exactly |
| `evidence_exists` | per case | a `pass` or `fail` has no evidence, a cited pointer was not loaded into the run, or its kind is not in `evidence_rules.allowed_sources` |
| `tools_in_scope` | per case | the definition fails the registry check, a tool mode is not offered, or the run blocked a source that needs a tool the agent lacks |
| `no_personal_data` | per case | the masker finds personal data in a rationale or pointer |
| `token_budget` | per case | a call was over `context.budget_tokens` or the run over `loop.budget_tokens` |
| `budget_never_exceeded` | component | a probe run with oversized inputs makes a call over the budget |
| `cited_sources_loaded` | component | a cited pointer, or a pointer in the trace, was never in a prompt |
| `memory_rows_masked` | component | a stored memory row holds personal data, or a row older than `retention_days` is not pruned (passes when system memory is off) |
| `stop_points_fire` | component | an approval point does not stop its item or finding in a replay, or a `fail` on a `high` item does not ask for a person |
| `verifier_catches_planted` | component | a planted finding (an unloaded source, a quote that is not in the source, a pass that breaks the pass rule) is accepted |
| `loop_stops_at_cap` | component | a loop that never converges runs past `max_iterations` or the budget, or a single pass runs twice |

The component tests run the real runtime with a scripted *probe model* (`supervisor.factory.probe`). It
tests the harness, not the agent; its answers are never stored as an assessment.

### Layer 2: judges, calibration, regression, floor

Two yes or no questions with a reason (masked, 200 characters) per case, on the gateway model:
`verdict_matches_expected` and `rationale_faithful_to_evidence`. The report also counts the cases where the
verdicts are exactly equal, so a judge that says yes to everything is visible. A judge call that fails
counts as `no` and in `judge_errors`.

| Rule (full gate) | Value | Gate |
|---|---|---|
| Calibration | the judge labels the human-labelled findings from the same sources; Cohen's kappa as an integer in hundredths (81 = 0.81) and the 4x4 confusion matrix (rows human, columns judge) | kappa >= `CALIBRATION_KAPPA_FLOOR` (70) and at least `CALIBRATION_MIN_LABELS` (20) usable labels |
| Regression | paired comparison with the live version of the same agent id on the same cases; a case is lost when the live version was accepted and the candidate was not | lost <= `MAX_REGRESSION_CASES` (2). The live results come from its newest passed full run on the same golden set (sha), else they are computed. No live version: no baseline |
| Tier floor | share of cases the judge accepts, for both questions | `high` tier 90 percent, `standard` 80 percent (`TIER_FLOOR_PERCENT`) |

`kappa = (n * agree - S) / (n * n - S)` with `S` the sum over verdicts of row total times column total;
integer arithmetic, rounded half up; one category and a perfect match is 100. Tier: `high` for the model,
cybersecurity and legal_compliance dimensions and for any agent with a `high` severity item. Judge and agent
both run on the gateway model (owner decision 5); the report states `same_family` so a reviewer sees it.
The verdict of the gate is a function of these integers; a judge never decides alone.

### Layer 3: shadow run

The candidate runs on the newest stored reports of its dimension under `DATA_DIR/assessments/<system>/
<attempt>/<dimension>.json` (one per system, N at most 25). The candidate reports are stored under the run
directory (`shadow/`), not shown. The report counts: systems, same worst verdict as the stored report,
different, **new fails** (candidate `fail`, stored not), fixed fails, and agreement with the status a person
confirmed in `risk_dimension_status` (`pass` or `fail`, `updated_by` not a rule). No stored onboarding is
`no_data`, not a failure. Layer 3 informs; it does not block.

### The report

`DATA_DIR/factory/<id>/gate/<run_id>/report.json`: signed JSON (`format:
supervisor.factory_gate_report`, `content_sha256`, Ed25519 `signature` of the evidence signer, like the
regulator pack) with integers, ids and enums only; verify offline with `python -m
supervisor.evidence.verify report.json`. The same directory holds `definition.json` (the tested
definition), `cases.json` (per case: match, faithful, exact, reasons) and `shadow/`. The `gate_run` row has
the layers, the cost (`model_calls`, `tokens_estimated`, `seconds`), `verdict`, `report_sha256`,
`signature` and `definition_sha256`. Each finished run writes the chain record `factory_gate_run`.

## Simulation review

Owner decision 5a. `POST /console/factory/{id}/gate/run` with `kind=simulation` and `systems=a, b` (1 to 10
systems of the inventory) runs the draft on the real run inputs of those systems (the system record, the
facts v1 export, the pack results of the rule proposal). The page
`/console/factory/{id}/simulation/{run_id}` shows, per system and finding, the verdict, the rationale and each
evidence pointer with the loaded text (masked, 300 characters). The reviewer marks the finding:

| Mark | Calibration label |
|---|---|
| `agree` | `human_verdict` = the agent's verdict |
| `disagree` | `human_verdict` = the verdict the reviewer holds correct (required) |
| `unsure` | none (an earlier label of the finding is removed) |

The note is at most 300 characters and masked. The marks are labels with source `simulation` (the inputs the
agent saw are kept in the run directory, so the calibration can re-read them) and a signed
`review_report.json` (counts, marks with hashed notes). The permission is `factory.edit` plus the group of
the agent; anyone who may read the factory reads the page. A simulation never promotes: its verdict stays
`not_run`.

## Promotion

```text
 draft --(full gate passed, this definition sha)--> tested --submit--> [approvals] --> approved --activate--> live
   ^                                                  |  reject / reopen / changed sha / failed gate |            |
   +--------------------------------------------------+----------------------------------------------+            |
 retired <-- supersede, retire, rollback ---------------------------------------------------------------------- live
 retired --rollback (admin, reason)--> live
```

| Move | Who | Condition | Refusal codes (HTTP 400) |
|---|---|---|---|
| draft to tested | the gate | a passed `full` run of this version and definition sha | `gate_not_passed` |
| submit | editor of the group (`factory.edit`) | state `tested`; the instructions name every checklist item | `not_tested`, `lint_not_ready`, `definition_changed` |
| approve `owner_lead` | approver of the owner group or admin (`factory.approve`) | submitted; not the author; not already given | `not_submitted`, `author_cannot_approve`, `already_approved`, `not_eligible`, `kind_not_required`, `definition_changed` |
| approve `second_line` | member of the `platform` group or admin (`factory.approve`) | as above; **a different person** from the first approval | `same_person`, plus the codes above |
| tested to approved | automatic | all approvals the change needs are given | |
| reject | owner lead, second line or admin (`factory.approve`) | state `tested` or `approved`; reason of at least 20 characters; approvals cleared, back to draft | `reason_too_short`, `not_eligible` |
| reopen | editor of the group | state `tested` or `approved`; reason of at least 10 characters | `reason_needed`, `not_eligible` |
| approved to live | owner lead or admin (`factory.approve`) | approvals complete, definition sha unchanged; the previous live version of the agent id becomes `retired` and stays readable | `not_approved`, `approvals_missing`, `not_eligible`, `definition_changed` |
| rollback | admin (`factory.rollback`) | a reason of at least 10 characters; the newest earlier retired version that was live becomes live, the live one becomes retired | `not_admin`, `reason_needed`, `no_previous_version`, `not_rollbackable` |

* **Approvals needed.** A `high` tier agent (see Layer 2) needs `owner_lead` and `second_line`, two different
  people. A `standard` tier agent needs `owner_lead`. A new version whose change against the newest earlier
  live version touches only the instructions or the checklist needs `owner_lead` only ("re-test, then the
  owner"). A change of the tools, the guardians, the harness permissions, the output schema or the tier needs
  the full approval again (`promotion.classify_change`).
* **Immutable versions.** Only a draft is edited. A tested, approved or live version changes only its state
  and its approvals. To change it, reopen it (back to draft) or make a new version (`new-version`).
* **Definition-change detection.** `definition_sha256` (the definition without `lifecycle`) is stored with the
  passed run. Submit, approve and activate compare it again; a difference sends the version back to draft
  (event and chain record `definition_changed`) and the answer is 400 `definition_changed`.
* **Failed gate.** A failed `full` run of a tested or approved version sends it back to draft.
* **Records.** Every move writes a `factory_agent_event` row (`tested`, `submitted`, `approval`, `approved`,
  `rejected`, `reopened`, `live`, `rolled_back`, `retired`, `definition_changed`) and the chain record
  `factory_promotion` (agent id, version, action, from, to, a keyed short hash of the actor, the definition
  sha, integers). Approvals are also in `lifecycle.approvals` of the version.
* **Orchestrator.** `live_agent_for(dimension)` returns the live version; with the flag on the Risk assessment
  tab passes `FactoryCatalog` to the orchestrator, so a live agent is planned as `<id>@<version>` and a
  dimension without one keeps the rule proposal.
* **Console.** RBAC rows: `factory.edit` (runs, marks, submit, reopen), `factory.approve` (approve, reject,
  activate; approver and admin), `factory.rollback` (admin). Every POST writes two `console_action` rows.
  The catalogue card shows the last gate result and the live version.

## Groups of a user

`config/users.yaml` accepts an optional `groups:` list per user (ids of `config/factory_groups.yaml`).
`store.permits(roles, owner_group, groups, user_groups)`: `admin` edits every group; a user **with** a
`groups:` list belongs to exactly those groups, whatever the role mapping says; a user **without** one falls
back to the `roles` mapping of the group. Example: `lead.model` has `roles: [approver]` and `groups:
[model_risk]`, so the user owns the model-risk agents and nothing else; `second.line` has `groups: [platform]`,
the second line of an approval. Synthetic users only; the Databricks App has no groups (role mapping).

  question). Every pack marked `required` for the dimension is mapped. The ethics group may now use

### Golden sets

`config/factory_agents/golden/<agent_id>/cases.json` (gate cases) and `calibration.json` (24 labels,
`label_by: synthetic.labeller`, three of them differing from the expected verdict, like a careful human).
Every item has 5 or 6 cases: pass, fail, question and, where the pass rule has an applicability clause,
not_applicable. A `fail` case has a source that shows the breach; a `question` case has only neutral sources.
`expected_evidence_refs` are refs of the case's own inputs (record fields `case-<case_id>.<field>`, fact ids,
pack refs, document sections). Synthetic Vietnamese text; the masker finds nothing in any case (a test
checks it). Regenerate (deterministic, seed 20261028, no model):

```text
python -m tools.factory_golden_gen            writes the files
python -m tools.factory_golden_gen --check    fails when a committed file differs
```

The scenarios are in `tools/factory_golden_specs.py`; a change there needs a regeneration and a commit.

### Seed

```text
python -m supervisor.factory seed
```

Needs `AGENT_FACTORY=1` and `GOVERNANCE_ENABLED=1`. For each of the eight ids that has no row in the
catalogue it creates the draft (validated like any other definition), copies the golden set into
`DATA_DIR/factory/<id>/golden/` and writes the events `created` and `golden_uploaded`. An id that already has
a row (any version) is skipped, so a team's edits and golden sets are never overwritten and a second call
changes nothing. Output: `[OK] created agent <id> (draft)`, `[OK] created template <id> (draft)`,
`[SKIP] <id> is already in the catalogue`.

`FACTORY_SEED_STARTERS=1` (default `0`; Windows cmd: `set FACTORY_SEED_STARTERS=1`) runs the same seed once at
startup when `AGENT_FACTORY` is on. A failure is logged and never blocks startup. Off: nothing is seeded.

### Gate on synthetic data (`--model fake`)

python -m supervisor.factory seed

`supervisor.factory.devfake.ReplayChat` (`model_id: dev-fixture-replay`): it looks up the golden case of the
